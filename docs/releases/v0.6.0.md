# 0.6.0 — Clientes e fornecedores (candidata)

A etapa 0.5 foi validada pelo usuário no Tab5. Esta etapa inclui cadastros online
com pesquisa paginada, consulta, edição, inativação/reativação e histórico de
alterações. Clientes inativos continuam no banco e no histórico. Nenhum dado
pessoal é gravado no microSD; formulário e página ficam na PSRAM durante a sessão.
Menu/sair/bloquear limpam formulários e registros da tela. Sem rede, operações
exibem erro e preservam o formulário para nova tentativa.

## Atualização do servidor instalado por ZIP

Copiar TAB5_ERP-v0.6.0-server-update.zip para /home/ubuntu/TAB5_ERP:

```sh
cd /home/ubuntu/TAB5_ERP
unzip -o TAB5_ERP-v0.6.0-server-update.zip
bash docker/scripts/update-contacts.sh
curl --fail https://tab5api.ampere.diadiatech.com.br/health/ready
```

O script faz backup antes da migração 003_contacts, constrói/recria a API e
verifica saúde. Preserva produtos, usuários, senhas, volumes e arquivos .env/secrets.
Não reimportar schema.sql nem apagar volumes. Atualizar a API antes do OTA 0.6.0.
A migração acrescenta contatos/vínculos, índices, permissões e concede somente as
novas permissões aos perfis Administrador/Gerente; demais atribuições são preservadas.
Usuários com sessões antigas devem sair/entrar para atualizar as permissões no Tab5.

## API e proteção de dados

GET/POST /api/v1/customers e /suppliers; GET/PUT/DELETE /{módulo}/{id}.
POST /{módulo}/search: q, document_query, after_id, limit e include_inactive.
Documento enviado no corpo da pesquisa pelo Tab5, evitando documentos na URL.
GET /{módulo}/{id}/history pagina eventos de alteração, sem conteúdo pessoal.
GET/POST /suppliers/{id}/products e DELETE /suppliers/{id}/products/{product_id}
consultam/criam/removem vínculos com produtos existentes; não movimentam estoque.

Campos: nome/razão social, PF/PJ, documento opcional, fantasia, telefone, e-mail,
endereço, cidade, UF, CEP, contato, observações, status, versão e datas. Fornecedor
usa PJ. CPF/CNPJ são texto: normalização de pontuação, dígitos verificadores,
CNPJ numérico e alfanumérico (ASCII menos 48), zeros à esquerda preservados.
Referência: https://www.gov.br/receitafederal/pt-br/centrais-de-conteudo/publicacoes/documentos-tecnicos/cnpj/manual-dv-cnpj.pdf
Validação não consulta cadastro oficial nem comprova existência/titularidade.

Permissões separadas customers/suppliers.read/create/update/delete/documents.
Listagens mínimas omitem documento/telefone/e-mail/endereço/observações. Detalhes
mostram documento somente com .documents; busca por documento também exige essa
permissão. Sem permissão documental, edição de outros campos mantém o documento
oculto existente. APIs auditam acesso ao detalhe e alterações sem gravar valores
pessoais na auditoria. Concorrência por versão rejeita alterações obsoletas (409).
Duplicidade por documento dentro de cada módulo retorna 409; documento opcional
permite múltiplos cadastros sem CPF/CNPJ. Mesma pessoa pode ser cliente/fornecedor.
Dados no servidor continuam sob as permissões de banco/backups da infraestrutura;
esses registros não têm criptografia adicional de coluna nesta etapa.

## Tab5

Menu Clientes / fornecedores; botão alterna o módulo quando permitido. Nome e
CPF/CNPJ exato podem ser pesquisados, com Mostrar inativos. Próxima/Primeira
página; detalhe com Editar/Inativar/Histórico. Reativar: editar e marcar Ativo.
PF/PJ e UF são campos de texto; documento não é obrigatório. Fornecedor tem
Produtos: informar o ID existente e Vincular/Remover vínculo. Consulta por toque
ou teclado físico; formulário rolável, teclado virtual e tema da sessão.
Histórico de compras/valores só existirá após a etapa de vendas 0.7; a tela informa
isso e mostra o histórico cadastral real, sem inventar compras ou totais.

## Validação

Testes da API cobrem documentos numéricos/alfanuméricos, dados opcionais,
duplicidade, CPF/CNPJ inválidos, UF/CEP/e-mail, pesquisa, paginação, permissões,
documento oculto preservado, edição/versão, inativação/reativação, histórico e vínculos.
CI inclui MariaDB real AMD64/ARM64 e backup/restauração. Firmware compilado para
ESP32-P4; dados de contatos em PSRAM, buffers de tela/DMA também em PSRAM.

Validação física pendente: cliente sem documento, PF com CPF válido de teste,
fornecedor PJ com CNPJ válido de teste; editar, pesquisar, inativar/reativar,
reiniciar e consultar, histórico e vínculo com produto; confirmar que ERP/cache
no cartão contém apenas produtos. Não usar documentos pessoais reais em testes.
