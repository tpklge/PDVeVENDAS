# 0.11.0 — Offline e sincronização (implementada; validação física pendente)

09/10/2026. Branch release/v0.11.0-offline. Base 0.10 aprovada pelo usuário.

## Atualização

Servidor ANTES do OTA, preservando .env, secrets, usuários, senhas, volumes e dados:

```sh
cd /home/ubuntu/TAB5_ERP
unzip -o TAB5_ERP-v0.11.0-server-update.zip
bash docker/scripts/update-offline.sh
curl --fail https://tab5api.ampere.diadiatech.com.br/health/ready
```

O script faz backup, build, migração 008_offline e verifica API/schema. Migração adiciona
sync_revision em produtos e epoch no catálogo; inicializa revisões existentes sem
reescrever preço, estoque, vendas ou credenciais. Não reimportar schema.sql/initialize.
Instale TAB5_ERP-v0.11.0-app-OTA.bin pelo launcher. Não apagar microSD ou NVS/partições.
Desbloqueio e conexão Wi-Fi/NTP/TLS mantidos; os novos arquivos usam a chave existente.

## Uso

1. Entre uma vez online no ERP com 0.11 e abra Produtos para criar cache criptografado.
2. Atualizar cache passa a buscar diferenças; exibirá quantidade alterada e revisão.
   A primeira atualização baixa tudo; só a lista paginada permanece na RAM.
3. Sem rede/API: na tela de login, Abrir offline usa o último perfil e o PIN já
   desbloqueado. Também disponível após reiniciar e tentar conectar. Menu mostra OFFLINE.
4. Produtos e pesquisa no PDV funcionam com dados do cache, cuja data/revisão é visível.
5. No PDV, monte carrinho e toque Salvar rascunho. Campos não salvos ainda ficam só em RAM.
   Carregar rascunho restaura itens, descontos, cliente informado e formas/valores.
   Excluir rascunho limpa cópias do cartão; Limpar carrinho só limpa a edição atual.
6. Para reconectar: Sair, Entrar no ERP, PDV, Carregar rascunho, Atualizar preços,
   revisar cliente/descontos/pagamentos, Revisar e cobrar, confirmar após receber.
   Abra caixa se necessário. Nenhuma venda/pagamento é concluído offline.
7. Uma tentativa desconhecida reaparece como pendente; Reenviar usa a MESMA chave.
   Resolver confirma ou abandona na API. Após conflito, resolver a tentativa e revisar
   o carrinho; não fabricar uma nova venda para substituir uma venda desconhecida.

Produto atualizado/inativado, preço, saldo ou permissão alterados exigem conferência.
A API é autoridade definitiva; sem reserva não garantir estoque pelo cache.
Rascunhos vinculados à tentativa impedem reapresentar uma venda confirmada como nova
após crash. Limpeza incompleta conserva a pendência. Não apaga arquivo corrompido sozinho.

## Persistência e limites

Ver [sincronização](../synchronization.md). Configurações continuam fora de NVS.
Cache, perfil e rascunhos AES-256-GCM; contexto API/dispositivo, operador para rascunho,
nonce de snapshot e posição para catálogo; footer SHA-256/quantidade para truncamento.
Chave derivada do PIN existente. Sem tokens/senhas ERP persistidos e sem documentos de
clientes/fornecedores no cache. Cache de produtos é compartilhado pelo terminal local
com PIN; acesso offline é uma autorização física de consulta, não autenticação ERP.

Um rascunho por operador; até oito produtos por carrinho e 10.000 no catálogo.
Fila segura atual: uma tentativa por módulo, serial, com retentativas explícitas.
Não há lote de vendas offline automáticas nem reservas, extratos/relatórios offline.
Sem novo menu complexo de filas; os estados e decisões aparecem nos módulos existentes.
Rascunhos/pendências bloqueiam trocar PIN/API/restaurar; excluir ou resolver antes.
Se PIN mudar após limpar rascunhos, reconstruir cache e confirmar novo perfil online.
Desconexão/interrupção descarta só temporários de cache; snapshot anterior é preservado.
FATFS usa flush/fsync e .bak; queda física de energia requer ensaio no Tab5, sem promessa
absoluta de atomicidade. Arquivo de cache danificado é preservado para inspeção ao
recuperar backup e concluir uma nova atualização; pendência financeira não faz rollback.

## API e restauração

GET /api/v1/sync/products com products.read, since, epoch, after_id, revision, limit
(1..25). Inclui inativos; alterações agrupadas pelo produto, sem log infinito.
Página seguinte exige revisão/epoch. 409 implica reiniciar sincronização; nada aplicado
no cartão antes do catálogo completo. Sem novas permissões ou concessões automáticas.

Depois de restaurar um backup em PRODUÇÃO, executar migrações e renovar catalog_state.epoch
com um UUID novo antes de reativar a API. Isso impede reutilizar revisões de uma história
que foi revertida. O procedimento está em docker/scripts/invalidate-sync.sh; não executar
na restauração isolada de CI que compara dados idênticos. Não altera dados comerciais.
