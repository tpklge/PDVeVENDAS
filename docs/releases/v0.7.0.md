## Atualização do servidor OCI por ZIP

Copie TAB5_ERP-v0.7.0-server-update.zip para /home/ubuntu/TAB5_ERP:

```sh
cd /home/ubuntu/TAB5_ERP
unzip -o TAB5_ERP-v0.7.0-server-update.zip
bash docker/scripts/update-sales.sh
curl --fail https://tab5api.ampere.diadiatech.com.br/health/ready
```

O script faz backup e aplica a migração incremental 004_sales, preservando
usuários, senhas, produtos, clientes, fornecedores e configurações do Traefik.
Não reimportar SQL, apagar volumes ou executar initialize novamente. Atualize o
servidor antes de instalar TAB5_ERP-v0.7.0-app-OTA.bin pelo launcher existente.

## Operação no Tab5

1. Entre no ERP e abra Vendas / PDV.
2. Informe ID do produto, quantidade e pressione Adicionar / editar. Para localizar
   por nome, use Pesquisar; toque no resultado para adicionar uma unidade.
   Tocar em um item do carrinho preenche seu ID; alterar quantidade substitui a
   quantidade anterior. Remover usa o ID informado. Limite: 8 produtos diferentes.
3. Cliente ID 0 permite venda sem identificação. Dentro da pesquisa, Buscar cliente
   permite pesquisar pelo nome e selecionar um cadastro ativo, conforme permissão.
4. Desconto do item e da venda podem ser em reais OU percentual, nunca ambos.
   A API aplica limite acumulado: Administrador 100%, Gerente 20%, outros perfis
   com sales.discount 10%; sem essa permissão, somente desconto zero.
5. Selecione os meios e valores dos dois pagamentos. Dinheiro, Pix, débito, crédito,
   transferência e outro; valores zero são omitidos. Apenas dinheiro pode gerar
   troco. A API suporta até 6 pagamentos e 20 itens por venda.
6. Calcular venda consulta o preço/estoque vigente e apresenta total para revisão.
   Finalizar venda confirma preço, versão, estoque, pagamentos e autorização outra
   vez, gravando toda a operação em uma transação. Sem rede não há venda offline.
7. Histórico consulta comprovantes não fiscais com valores originais. Cancelar
   venda exige sales.cancel, justificativa e confirmação; repõe estoque uma única
   vez e registra reversão gerencial dos pagamentos. Não confirma reembolso externo.

O produto precisa ter estoque suficiente. Atualize seu saldo em Produtos usando
um perfil com inventory.adjust; essa operação também produz movimento auditável.
Atualizar preços no PDV exige conferir novamente os valores antes de finalizar.
Pagamentos são declarações do operador; não existe autorização automática por
adquirente/Pix, integração fiscal, captura de dados de cartão ou devolução parcial.

## Recuperação de tentativa interrompida

Antes de enviar, o Tab5 grava apenas IDs, quantidades, preços/descontos, pagamentos
e chave de idempotência em /sdcard/ERP/pdv/pending.enc, AES-256-GCM com a chave
local desbloqueada pelo PIN. Não usa NVS. O registro é vinculado ao operador,
dispositivo e API; nomes de clientes, documentos e tokens não entram no arquivo.

Após timeout/reinício, entre com o mesmo operador/API. Reenviar usa exatamente o
mesmo pedido/chave. Resolver tentativa consulta a API: recupera a venda já concluída
ou encerra essa chave transacionalmente, impedindo que um envio atrasado crie uma
venda depois da resolução. Só então permite nova tentativa. Não remova o arquivo
para contornar uma pendência. Erro de cartão/escopo bloqueia nova venda.

Uma pendência bloqueia alteração do PIN, URL da API e restauração local até ser
resolvida; Wi-Fi pode ser reconfigurado. Configurações e pendência ficam no microSD,
vendas e movimentos definitivos ficam no MariaDB. Carrinho ainda não enviado fica
somente em RAM. Backup do servidor cobre vendas, itens, pagamentos e movimentos.

## API e validação

POST /api/v1/sales/quote; POST/GET /api/v1/sales;
GET /api/v1/sales/{id}; POST /api/v1/sales/{id}/cancel;
POST /api/v1/sales/requests/{key}/resolve;
GET /api/v1/customers/{id}/purchases (customers.read e sales.read).

Valores monetários usam Decimal/HALF_UP na API e inteiros na interface.
Transações travam o catálogo/produtos em ordem consistente; saldo insuficiente,
versão/preço alterados e pagamentos inválidos não deixam gravações parciais.
A migração registra o saldo anterior como movimento de abertura.

Testes automatizados incluem persistência da migração, rollback após falha,
permissões/descontos, snapshots, troco, histórico, cancelamento repetido e barreira
contra envio atrasado. CI testa concorrência e idempotência em MariaDB AMD64/ARM64,
além de restaurar backup da stack. A aprovação física desta etapa ainda está pendente.

Teste no Tab5: venda de 190 com dinheiro 200 (troco 10), venda mista, desconto,
saldo insuficiente, repetição de tentativa, reinício com pendência, histórico,
compras do cliente e cancelamento com estoque reposto uma vez.
