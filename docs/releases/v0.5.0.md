# 0.5.0 — Produtos (candidata)

A etapa 0.4 foi validada pelo usuário no Tab5. A etapa 0.5 precisa de atualização
da API para 0.5.0, migração incremental 002_products e firmware 0.5.0.
Usuários, senhas, configurações do cartão e banco existente são preservados.

## Servidor instalado por ZIP

Copiar TAB5_ERP-v0.5.0-server-update.zip para /home/ubuntu/TAB5_ERP e executar:

```sh
cd /home/ubuntu/TAB5_ERP
unzip -o TAB5_ERP-v0.5.0-server-update.zip
bash docker/scripts/update-products.sh
```

O script faz backup do MariaDB antes de migrar, constrói a imagem, para apenas
a API, executa Alembic/seed e recria a API com verificação de saúde. Há breve
indisponibilidade. Não importa schema.sql no banco existente, não apaga volumes,
não modifica .env/secrets e não redefine senha. Se houver falha de migração,
não apagar tabelas ou repetir importação de schema; coletar a saída do script.

## API e dados

GET/POST /api/v1/products; GET/PUT/DELETE /api/v1/products/{id}; GET/POST
/api/v1/categories; PUT /api/v1/categories/{id}. Query de produtos: q, category,
after_id, limit, include_inactive e revision. Paginação por ID e revisão do
catálogo: mudança durante leitura retorna 409 para evitar snapshot misto.

Cadastro inclui SKU, GTIN opcional, nome, descrição, categoria, unidade, custo,
venda, estoque atual/mínimo/máximo, ativo, NCM, CEST, origem e datas. Fiscal é
apenas metadado: não se calculam impostos nesta etapa. SKU normalizado para
maiúsculas, GTIN com comprimento e dígito verificador, duplicidade bloqueada.
Preços em DECIMAL(12,2), quantidades em DECIMAL(15,3), sem cálculos monetários
com float. Backend rejeita negativos, excesso de precisão e máximo menor que
mínimo. Categorias podem ser criadas ao informar um nome novo no produto.

Permissões products.read/create/update/delete por endpoint. Ajustar estoque
existente exige inventory.adjust. Edição exige versão atual; versão antiga
retorna 409. Inativação preserva cadastro e histórico, sem delete físico.
Operações bem-sucedidas são auditadas. Movimentos de estoque, vendas e tributos
pertencem às próximas etapas.

## Tab5 e cache

No menu Produtos, filtrar por nome/SKU/GTIN e categoria, mostrar inativos, paginar,
consultar, cadastrar, editar ou confirmar inativação. Formulário rolável com
teclado virtual e físico. Preços aceitam vírgula ou ponto, sem separador de milhar.
Campos digitados são preservados após erro. Permissões controlam botões e API.

Cache JSONL em ERP/cache/products-<hash-da-URL-API>.jsonl. API é fonte de verdade;
cache serve para consulta de catálogo e não autoriza venda/preço/estoque futuro.
A consulta mostra data UTC e revisão. Login ERP continua exigindo API; consulta
sem rede está disponível durante a sessão já autenticada. Salvar/inativar exige
rede e confirmação da API; não há fila de gravações offline nesta etapa.

Atualizar cache obtém snapshot completo com páginas de 2 registros e consulta
local mostra 8 registros por página. Arquivos são percorridos linha a linha;
não se carregam milhares de produtos na RAM. Limite explícito de 10.000 registros
por cache, com erro sem substituir a cópia anterior se excedido. Snapshot de
catálogo grande pode demorar; progresso permanece visível e sair cancela no
próximo intervalo entre requisições. Token é renovado durante leitura longa.

Gravação temporária, flush/fsync, rename e .bak preservam a cópia anterior em
falha; queda de energia/remover cartão ainda pode corromper FAT. Cache não inclui
senha, token ou dados pessoais. Backup: desligar e copiar toda a pasta ERP do
cartão; banco exige backup próprio. Configurações continuam criptografadas.
