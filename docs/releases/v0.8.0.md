## Atualizar o servidor antes do OTA

Copie TAB5_ERP-v0.8.0-server-update.zip para /home/ubuntu/TAB5_ERP:

```sh
cd /home/ubuntu/TAB5_ERP
unzip -o TAB5_ERP-v0.8.0-server-update.zip
bash docker/scripts/update-inventory.sh
curl --fail https://tab5api.ampere.diadiatech.com.br/health/ready
```

O script faz backup, constrói a API, aplica 005_inventory e recria/verifica a API.
A migração acrescenta resultados idempotentes e resolução de tentativas, preservando
usuários, senhas, produtos, contatos, vendas e todos os movimentos existentes.
Não reimportar SQL, apagar volumes ou executar initialize novamente.
Depois, instalar TAB5_ERP-v0.8.0-app-OTA.bin pelo launcher existente.

## Operação no Tab5

1. Abra Estoque, pesquise e toque no produto. As páginas carregam até 8 registros.
2. Entrada acrescenta uma quantidade; Saída retira uma quantidade. Ambas exigem
   quantidade positiva, com até 3 casas decimais (ponto ou vírgula).
3. Contagem / ajuste informa o saldo TOTAL contado, que substituirá o saldo atual;
   zero é permitido. O formulário inicia com o saldo atual, evitando ajuste acidental.
4. Informe justificativa obrigatória e toque Revisar movimento. Confira saldo
   anterior, quantidade/saldo contado e saldo previsto; Confirmar movimentação grava.
5. Histórico inclui saldo inicial, ajustes cadastrais, entradas, saídas, contagens,
   vendas e cancelamentos. Toque no registro para abrir a justificativa completa.
6. Mínimo/máximo continuam configuráveis em Produtos. Estoque baixo significa
   saldo menor ou igual ao mínimo. Produtos inativos mantêm consulta/histórico.

Após movimento, o comprovante mostra os saldos registrados naquele momento.
Consulte novamente o produto antes de movimentar outra vez: venda ou outro operador
podem ter alterado seu saldo. Operações exigem API online; não existe baixa offline.
Permissões: inventory.read para consultar; inventory.adjust para movimentar.
Preços de custo/venda não são expostos pela consulta de estoque.

## Recuperação no microSD

Antes de enviar, o Tab5 grava a tentativa em /sdcard/ERP/inventory/pending.enc,
criptografada com AES-256-GCM, vinculada ao PIN desbloqueado, operador, dispositivo
e URL da API. Guarda IDs, versão, quantidade, justificativa e chave da tentativa;
não guarda tokens ou senhas. O formato das configurações e pendências de venda
anteriores é preservado. Não usa NVS para configurações ou pendências.

Após timeout/reinício, Reenviar usa exatamente o mesmo pedido/chave. Resolver
retorna o movimento concluído ou encerra a chave na API antes de permitir nova
tentativa. Essa barreira impede um envio atrasado de alterar o saldo após resolução.
Erros de cartão/escopo preservam a pendência e bloqueiam novo movimento.
Uma pendência de venda OU estoque bloqueia troca do PIN, URL e restauração local;
Wi-Fi pode ser reconfigurado. Saldos e movimentos definitivos ficam no MariaDB.

## API e integridade

GET /api/v1/inventory; GET /api/v1/inventory/{id};
GET /api/v1/inventory/{id}/movements; GET /api/v1/inventory/movements/{id};
POST /api/v1/inventory/adjustments; POST /api/v1/inventory/requests/{key}/resolve.

Entrada/saída usam quantity positiva; contagem usa target_quantity maior ou igual
a zero. Toda mutação exige versão atual, justificativa e chave idempotente.
Mesmo pedido/chave retorna o movimento original; corpo diferente é recusado.
Saldo, movimento, auditoria, revisão e resultado são gravados na mesma transação.
Bloqueios são compartilhados com vendas; saldo negativo não é permitido.
READ COMMITTED no MariaDB mantém os bloqueios compatíveis com envios simultâneos.
